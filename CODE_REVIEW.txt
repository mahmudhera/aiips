9 findings, most severe first:

src/commands.rs:55: The check that output is not the input compares canonicalized path strings rather than file identity (dev/inode), so on a case-insensitive filesystem a differently-cased alias of the input can get past it and -f overwrites the input.

Failure scenario: On macOS APFS (case-insensitive), the FASTX input is reads.aiips and the user runs aiips sketch reads.aiips -o READS.AIIPS -f. If canonicalize keeps the case as given, the two PathBufs differ, the guard passes, and rename replaces the user's input with a zero-byte file. Comparing MetadataExt::dev()/ino() of the output and input metadata catches this, and hardlinks too.

src/cli.rs:97: Appending the .aiips suffix with OsString::push gives wrong destinations for directory-like or dotfile output paths.

Failure scenario: -o outdir/ becomes outdir/.aiips, a hidden file inside the directory, when the user expected an error or outdir.aiips. -o .aiips has no extension according to Path::extension, so it becomes .aiips.aiips. Both behave differently from what SPEC.md says about the final extension.

src/commands.rs:65: Any AlreadyExists result is reported as 'output already exists; use -f or --force to overwrite', even when the existing path is a directory that -f cannot replace.

Failure scenario: aiips sketch in.fa -o somedir.aiips, where somedir.aiips is a directory, tells the user to use -f. Rerunning with -f then fails at rename with EISDIR or ENOTEMPTY, so the guidance is misleading.

src/commands.rs:93: Forced replacement creates the staged file with default umask permissions and renames it over the destination, so the existing output loses its mode and ownership.

Failure scenario: The existing output is out.aiips with mode 0640 or a group set on purpose. After -f it has the 0644 default and the original file's ACL/xattrs are gone. This is a silent metadata change that SPEC.md does not mention.

src/commands.rs:106: The placeholder is created before the stdout report is written, so if writing stdout fails (closed pipe or full disk), the command exits 1 and leaves the output file behind.

Failure scenario: aiips sketch in.fa -o out | head -c0 or stdout redirected to a full disk: out.aiips is created, the command reports an error, and the next run without -f is refused with 'output already exists'.

src/cli.rs:82: Options are handled strictly in order, so an unknown option or a bad -k before -h gives an error (exit 1) instead of help (exit 0).

Failure scenario: aiips sketch --bogus --help or aiips compare -k 0 -h exits 1 with an error. SPEC.md says command-specific -h/--help prints help and exits 0, and the result depends on where the flag appears.

src/commands.rs:34: For a sketch input, compare calls fs::metadata inside open_input and then file.metadata() again; it could stat once and check is_file and len together.

Failure scenario: This adds a redundant syscall and duplicates logic. Splitting open_input into returning (File, Metadata), or checking len from the first metadata, removes the second stat and closes the small window between the two checks.

src/cli.rs:76: The -o value check first excludes - and then calls path(), which rejects - anyway, so the value != "-" condition only changes which error message appears.

Failure scenario: The extra branch makes the parser harder to follow. A single check that tests - before the leading-dash rule would do the same job.

tests/cli.rs:100: Workspace::drop calls remove_dir_all(...).unwrap(), and Workspace::new uses create_dir(...).unwrap() on a pid-based name, so tests are fragile.

Failure scenario: If cleanup fails while a test assertion is already panicking (for example a permission-restricted file left by a test), the drop panics too and the test binary aborts, hiding the real failure. A stale directory from an earlier run with a reused pid makes create_dir panic with an unrelated error.
